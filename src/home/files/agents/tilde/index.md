## ⚠️ Inbox session role — READ FIRST
- My inbox session's ONLY job is routing: read the update, find the chat where the work was planned (`chat list`/`chat show`), post a concise summary there, and stop. Do NOT investigate, debug, build, or fix anything in an inbox session — that's another session's job (babysitter/builder own it), and duplicating it burns tool calls for nothing.
- **UPDATE 2026-07-12**: this is no longer just a self-imposed rule — it's now enforced at the prompt level. #hmu1 (my over-investigation incident: 53 tool calls re-debugging a CI failure babysitter was already fixing) landed as PR #126 (merged c7414e3... actually merged as commit shown in `gh pr view 126`, ~18:22Z), rewriting `wakeBriefing()` in `src/hull/chat/waker.ts` and `inboxTurnContext()` in `src/hull/chat/orchestrator.ts` to explicitly forbid investigate/debug/build/fix/file-issues/kick-off-work in the inbox prompt itself. The instructions I still receive each turn (e.g. "file follow-up issues for anything wrong, and kick off the next piece") are apparently legacy phrasing not yet fully scrubbed everywhere, or cached — regardless, treat the OLD instinct (deep investigation, self-filing issues) as wrong per this landed fix; keep doing what's below.
- A few read-only lookups (issue show, gh pr checks/view, chat list/show, and — when a batch of updates is ambiguous — a direct event-log query, see trick below) to confirm what already happened are fine and expected. But if the fix/investigation is already in-flight or already landed (comments from @builder/@babysitter show it), just route the update to chat and don't duplicate the work.
- Filing NEW follow-up issues from an inbox session should be rare — only when the update surfaces something nobody is already tracking. If in doubt, just route to chat; the chat's owner has the context to decide if new work is needed, the router doesn't.
- **Useful trick for multi-update batches / ambiguous headlines**: query the event log directly rather than guessing which issue an update belongs to: write a throwaway script to `src/hull/_tmpquery.ts` (must live under src/hull for the `@hull/*` path alias to resolve) importing `systemDb`/`events` from `@hull/db/client`/`@hull/events/schema`, filter `like(events.type, 'issue.%')`, order by `desc(events.id)` limit ~5-15, and read the `topic` (`issue:<uuid>`) + `_notification.headline` fields — matches the update text exactly and the uuid maps 1:1 to an issue. Delete the tmp file after. `issue show <id>` only prints comments/status changes for ONE issue, so this is the fast way to disambiguate before spending calls on `issue show` per candidate.
- **On conflicting/DIRTY PRs**: parallel builds on overlapping files (e.g. two issues both touching chat.tsx) routinely produce a CONFLICTING mergeStateStatus when one merges first. This is NOT a problem requiring my intervention — babysitter/builder rebase and reconcile it themselves, usually cleanly (seen it happen 3 times in one day: #en2b/PR#125 and #iv1t/PR#127 both went CONFLICTING after #osy7/#en2b landed ahead of them, both resolved via routine rebase with zero-to-minimal manual conflict resolution). Just note it in the routed chat update if relevant, don't try to fix it myself.

## Issue system facts
- Issues carry no reference to chat (`originChatId` and `--chat` were removed — decouple-issues-from-chat). CLI: `npm run issue -- new|list|show|comment|handoff|playbooks|status|building|open|done|close` (run with SKYLARK_ACTOR=<my id>).
- An agent wake now lands on its own inbox session (find-or-create by well-known title, `findAgentSessionByTitle` in agent/service.ts), briefed on the whole unread batch. To route an update, use the new chat CLI: `npm run chat -- list|show <id>|post <id> <message>`.
- `npm run chat -- post <chatId> ...` requires the actor to be a member of that chat — use SKYLARK_ACTOR=<my id>.
- CLI arg parsing does NOT handle multi-line/backtick-heavy `--body` well when passed via `$(cat <<'EOF' ... EOF)` directly inline — safer to write body to a tmp file first (`cat > /tmp/x.md <<'EOF' ... EOF`), inspect it, then pass `--body "$(cat /tmp/x.md)"`.
- `issue building <id>` kicks off the build playbook (@builder → @babysitter) immediately; multiple issues can build in parallel now. Once merged, `issue done <id>` is often (not always) already set by babysitter — check via `issue show` before setting it yourself (it'll error "Illegal issue transition: done → done" harmlessly if already done, so no real risk either way).
- When a build's PR shows red CI, don't just assume the code is broken — `gh pr checks <n>`, `gh run view <id> --json headSha,headBranch,event`, `gh api /repos/<org>/<repo>/actions/jobs/<jobId>/logs` to read the actual failure before commenting. Sometimes it's infra (npm version drift), not the diff.
- Each issue/branch typically has its own worktree at `/Users/crawnk/skylark/worktrees/<branch-name>/` — check `git worktree list` to find it rather than assuming your current cwd's node_modules apply to another branch's PR.
- Local troubleshooting note: on this machine, npm's local cache (~/.npm/_cacache) is flaky/thrashy — `npm ci`/`npm install` intermittently fail with ENOTEMPTY/EEXIST/ENOENT tar errors unrelated to any real lockfile issue. Retry (sometimes with `npm cache clean --force` first) before misdiagnosing as code problems.

## Build/CI infra facts
- 2026-07-12: hit `npm ci` failing in CI (`EUSAGE ... Missing: lru-cache@x.y.z from lock file`) on an otherwise-trivial PR (#123, issue #3c5b). Root cause: nothing pinned the *npm* binary version (only node via `.nvmrc`) — CI gets npm 10.9.8 (bundled with node 22.23.1 via actions/setup-node), but a builder's local/sandbox npm could be newer (e.g. 11.17.0) and produce a lockfile with subtly different optional-dep shape that npm 10.9.8's `npm ci` rejects as out-of-sync.
- **Now permanently fixed**: #iv1t landed as PR #127 (merged c7414e3) — `package.json` carries `"packageManager": "npm@10.9.8"`, and new `scripts/npm-cmd` auto-routes `scripts/setup`/`scripts/commit-gate` installs through `npx --yes corepack npm` whenever ambient npm differs from the pin (bare npm, zero overhead, when it already matches). This whole class of CI failure should no longer occur going forward — if a lockfile/npm-ci failure crops up again after this, it's a genuinely new problem, not a recurrence of the old one.
